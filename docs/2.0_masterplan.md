# Product Requirement Document: PD Noise Generator v2.0 (Agentic Edition)

**Context:** We have reset the codebase to v1.8.2. We are building a new v2.0 architecture on top of this foundation. 
**Core Philosophy:** "Tactical AI, Strategic Speed." We use GenAI as a **Design-Time Agent** to build scenarios, but use deterministic **Faker libraries** for the **Run-Time Execution** to ensure high performance (100+ events/min) without hitting LLM rate limits.

## 1. The "Hybrid" Architecture

*   **Design Time (Slow & Smart):** A "Demo Agent" (Gemini) converses with the user to design failure scenarios (e.g., "Build a Black Friday database crash"). It outputs structured templates containing dynamic tokens.
*   **Run Time (Fast & Dumb):** A local `FakerService` replaces tokens (e.g., `{{faker.internet.ip}}`) in milliseconds during the simulation loop. No external API calls are made during noise generation.

## 2. Data Taxonomy (New Schema)

We are moving away from flat file storage to a relational hierarchy to support complex demos.

*   **Domain:** High-level grouping (e.g., "Retail Banking", "E-Commerce", "Logistics").
*   **Team:** The specific owning squad (e.g., "Checkout Team", "Platform Ops").
    *   *Attribute:* **Persona** (Defines the tone of ChatOps/Slack messages, e.g., "Anxious", "Professional").
*   **Service:** The technical entity (e.g., "Payment Gateway API").
    *   *Attribute:* **IntegrationKey** (PagerDuty Routing Key).
*   **PayloadTemplate:** The reusable JSON pattern.
    *   *Content:* `{"error": "Connection Refused", "ip": "{{faker.internet.ip}}"}`
    *   *State:* Draft (User testing) vs Active (Live simulation).

## 3. Key Modules & Roadmap

### Phase 1: The Foundation (Taxonomy & Engine)
**Goal:** Establish the database structure and the high-performance rendering engine.

*   **Backend:**
    *   Implement Prisma Models: `Domain`, `Team`, `Service`, `PayloadTemplate`.
    *   Implement `FakerService`: A utility that takes a string with `{{mustache}}` syntax and renders a pure JSON object using `@faker-js/faker`.
*   **Frontend:**
    *   "Configuration" Page: A CRUD UI to manage Domains, Teams, and Services manually.

### Phase 2: The Agentic Campaign Builder
**Goal:** Replace manual form-filling with an AI Agent.

*   **Workflow:**
    *   **Chat Interface:** User types "Create a scenario where the Search API has high latency due to a memory leak."
    *   **Agent Logic:**
        *   Generates a TL;DR summary for approval.
        *   Generates the Change Events (Deployments) and Alerts (Metrics).
    *   **Bridge:** The Agent populates the existing "Campaign Editor" UI with these proposed events.
    *   **Refinement:** User reviews the Agent's draft, tweaks timestamps/keys, and saves it as a "Failure Campaign."

### Phase 3: Director Mode (The Soundboard)
**Goal:** Real-time, clickable interaction for live demos.

*   **UI:** A "Soundboard" Dashboard organized by the Hierarchy (Domain > Team).
*   **Features:**
    *   **Draft Testing:** "Test Fire" a button to see the payload in the console before sending to PagerDuty.
    *   **Live Injection:** Click a specific failure card (e.g., "Database Lock") to inject that event immediately into the active simulation.

### Phase 4: Persona-Based ChatOps
**Goal:** Make the "War Room" chatter feel distinct for every team.

*   **Logic:** When an incident triggers, the system generates a Slack message using the Team's Persona (defined in Phase 1).
    *   *Checkout Team:* "Omg looking at logs now!!" 😱
    *   *SRE Team:* "Acknowledging alert. Investigating elevated error rates."

## 4. Technical Constraints

*   **Performance:** The main generation loop MUST NOT await external API calls (LLMs). All templates must be pre-rendered or rendered locally via Faker.
*   **Persistence:** All configurations must be saved to PostgreSQL (via Prisma).
*   **Security:** API Keys (Gemini, PagerDuty) must be managed via `.env` or encrypted DB fields.
